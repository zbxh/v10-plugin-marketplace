# 从零开发 V10 插件

## 把初步想法变成首版方案

1. 从用户描述中提取使用者、操作入口、触发条件和预期结果。结合项目中的原生流程，给出首版要解决的场景和可执行的验收步骤。若同时涉及后台与会员端，分别写清两侧能看见、能配置和能操作的内容。
2. 在方案中写出会影响行为的规则和默认值。例如谁有权限、什么时间生效、失败或重复操作如何处理、历史数据如何保留。涉及订单或金额时，明确支付、退款、开票和收益口径。只有会改变架构或业务结果的歧义需要先问用户，可逆的细节可以标为暂定。
3. 验证原生流程是否具备所需扩展点。记录模块类型、候选钩子或接口、调用方、关键参数和限制。需要外部接口时，明确插件负责到哪一步以及可用的测试替代方式。V10 版本、测试站或商城版本号未指定时，可以先核对现有环境并推进不依赖这些信息的设计或源码工作。
4. 用户仅要求讨论时，交付产品方案或功能清单。用户要求实现时，确认不冲突的插件标识，按现有仓库约定创建插件目录，做出首个完整业务场景。插件较复杂时再增加数据关系、状态和验收矩阵等设计资料。

以「想做一个产品到期提醒插件」为例。管理员选择商品、提前天数和通知渠道，系统在目标日期生成一条待发送通知，后台显示结果。按业务确认同一服务续期后能否再次提醒，然后在同一到期周期重复执行调度，验证只生成一次通知。通知渠道实发及更多提醒方式按本轮需求纳入。

## 选择模块和首个原生入口

| 场景 | 常见入口与核对点 |
| --- | --- |
| 给现有订单、会员、财务后台或定时任务增加能力 | 先看 `addon`。从业务调用处找钩子，确认参数、执行时间和返回结果如何被消费。 |
| 自定义可购买的商品、调用供应商接口开通或续费 | 先看 `server`。跟踪商品配置、定价、订单履约和服务状态的实际模块调用。 |
| 提供支付、登录、邮件、短信或发票渠道 | 找对应模块的现有实现和原生分发入口，按其接口和元数据搭建。 |

同类插件用于核对契约。已有目标插件应沿用其模块和标识。新 addon 用 `get_plugin_class()` 验证目录名、PHP 文件名、命名空间、类名和 `$info['name']` 对齐，先检查是否与现有插件冲突。[插件开发](development.md)

## 从入口文件做到可操作的首版

1. 可从 [最小 addon 模板](../assets/addon/ExamplePlugin.php) 起步。复制到插件目录，换掉 `example_plugin`、`ExamplePlugin`、文件名和插件资料。示例版本 `0.0.0` 仅用于开发识别。模板只声明插件信息和生命周期入口。其他模块按目标 V10 的各自契约初始化。
2. 按首个场景创建需要的文件。简单配置可沿用平台支持的 `config.php`。有业务页面时，从同版本的独立插件核对导航、权限、路由、控制器和模板；有独立状态时，再定义数据表和迁移。对一个受控入口先完成参数校验、保存或调度、结果显示及权限验证。
3. 通过目标环境的原生入口跑通首个场景。比如从后台找到应用并安装，以允许的角色保存规则，生成虚构样本，观察业务结果和可读日志。通过后再覆盖同类场景和异常路径。首版使用教程与测试步骤以这一实际路径为准。[测试验收](acceptance.md)
4. 首发若准备上商城，在入口与包结构尚易调整时核对授权接入约定。用户指定对外版本后，使用该版本的候选包做纯净站安装并保留哈希，作为后续升级的首个真实基线。[商城打包](marketplace.md)
